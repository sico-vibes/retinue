# Lessons (living log)

Newest first. One entry per lesson: date, area, symptom, root cause with evidence, fix, how to avoid it. Before adding, search this file; if an entry covers the topic, update it. Remove entries that stop being true (the history stays in `docs/history/`).

## 2026-11-13 · Lanes · Eight backend lanes at once: what merging them took

Eight backend lanes ran in parallel in the in-app backend bot, one git worktree each (12 November 2026). What mattered:

- **Retinue runs four bots at once by default** (`concurrency.botsAtOnce`, 1 to 16, the owner's setting). A message past the limit is refused with "this one will start when one finishes" and is **not** queued: the conversation is created empty. Ask the owner to raise the limit, or send again when a slot frees.
- **Two of eight lanes ended with "tests are running, I'll report" and no report.** Their work was complete in the worktree. Read the diff; do not wait for the message.
- **Lanes edit shared files.** Six touched `main.rs` and all touched `docs/ipc-contract.md`. Merge by exporting each lane's diff (`git add -N` its new files first) and applying them in turn with `git apply --3way` in one integration worktree that already has a warm `target`. Almost every conflict was two lanes adding beside each other (keep both); the real one was two lanes each asserting the other's provider could not steer.
- **A lane's tests can contradict another lane's feature.** After merging, one test still used Claude as "an agent that cannot steer". Run the merged suite, not each lane's.
- **Lanes drift outside the brief** (skill files, generated docs, bridge files). Export only the paths the brief allowed.

## 2026-11-13 · Gates · Smart App Control blocks some freshly built binaries, not all

It is intermittent, not total: on 12 and 13 November `cargo check -p retinue-daemon` and the daemon and storage unit tests built and ran (1,033 and 164 passed), while several integration test binaries (`acp_lifecycle`, `acp_steering`, `table_providers`, `wire_replay`, `daemon_smoke`, `parent_watchdog`) and every build script of the native shell (`tray-icon`, `tauri-runtime-wry`, `retinue-desktop`) were refused with os error 4551. So on this machine the native shell cannot be compiled at all, and native changes are only proven by CI or a release build. Use `cargo test --no-fail-fast`, or one blocked binary hides every suite after it. The opt-in live Claude test did run: `RETINUE_LIVE_TESTS=1 cargo test -p retinue-adapter-claude --test live_suite claude_live_permission_change_and_steer` passed, which is the proof that steering reaches a real Claude Code turn.

**Workaround when cargo stops on a blocked build script (13 November 2026):** delete that build script's folder and retry, so cargo compiles it afresh — `Remove-Item -Recurse -Force 'target\debug\build\getrandom-<hash>','target\debug\build\serde_json-<hash>'`, then the same `cargo test` passed; the newly compiled script was allowed where the old binary was not. A fresh binary compiled outside the repo (`cargo new` in `C:\tmp`) ran at once, so the block is per binary, not per path. Retry before giving up on a suite.

## 2026-11-13 · Gates · Two daemon tests fail when run from inside the app's own environment

`doctor::tests::database_and_hook_rows_are_one_line_and_actionable` and `remote::tests::an_absent_web_folder_serves_the_built_in_page` failed (1045 of 1048 passed) when `cargo test -p retinue-daemon --bin retinued` ran in a lane started by the installed app. Cause: the lane inherits the running app's environment — `RETINUE_HOOK_BRIDGE` and `RETINUE_REMOTE_WEB_DIR` — so `hook_checks` finds a hook where a test binary has none, and `StaticFiles::from_env` loads the real `remote-web` folder instead of the built-in page. ## 2026-11-11 · Work log · A turn that ended kept saying "Working"

Symptom: a finished turn's work-log line read "Working · Ran 153 commands" for ever. Cause: `groupConversationActivity` (`ui/conversation.ts`) took any step whose last report was "running" at its word, and a turn that ends while its sub-agents are still open leaves such steps behind. Fix: the function takes what is live (false, true, or the running turn's id); a step in a turn that is not running is shown as "Did not finish". While a turn runs, only the newest group or the one with its turn id can be working.

## 2026-11-11 · Composer · The queue could vanish on first load: the first snapshot overwrote it

Symptom: in the preview, `?scene=queue` sometimes showed no queued messages until one was added. Cause: `loadQueue` (`ui/App.tsx`) had already stored the queue when the first-load path ran `setSnapshot(initial)` again (React StrictMode remounts in dev; any second initial load does it), and a fresh snapshot carries no queues. Nothing reloaded it, because the conversation and connection had not changed. Fix: that write goes through `carryQueues(initial, current)`, like every other snapshot refresh. Rule: never write a whole snapshot without `carryQueues`.

Also learned: "Send now" from a queue row is two existing calls in the window, `session.steer` then `session.queue.delete`, in that order so a failure leaves the message in the queue. A plain refusal (`unsupported`, `conflict`) falls back to `session.queue.send_now`. This is a stopgap until the daemon does it in one step. `session.limit.resume` and `session.limit.snooze` exist only in the preview bridge. Editing a queued message in the box writes through the draft store, so a `beforeunload` handler restores the earlier draft before the store flushes on `pagehide`. A daemon error code is the prefix of the message (`conflict: ...`), which is what a test must throw.

## 2026-11-08 · Storage · A new proposal kind needs two lists and a CHECK

Adding `hire` (Phase 9) failed at run time with "The proposal could not be recorded: invalid agent", although the `proposals` table had been rebuilt with the new kind. Three places decide a kind: the table's `CHECK(kind IN (...))` in the DDL **and** in the rebuild branch of `ensure_proposal_schema`, the `ddl.contains("'<kind>'")` test that decides whether to rebuild at all, and the plain allowlist in `Storage::insert_proposal` (`lib.rs`, one array of kind names). The third one raises `InvalidAgent`, which the daemon reports as a validation failure rather than a schema problem. **To avoid:** grep for every list of proposal kinds (`"permission", "merge"`) when adding one, and add a test that only creates that kind (the storage suite alone found nothing, because `ensure_proposal_schema` passed).

## 2026-11-08 · Looks · `valid_look` refuses a `style` key, so a preset cannot carry `{"style":"haze"}`

Haze is a *look theme*, chosen in the UI; the stored `agents.look` is `{shape, seed, traits, bot, art, paint, icon}` and `valid_look` rejects any other key. A Haze portrait is therefore `{"shape":"circle","icon":"char-..."}`. The same shape is what `normalizeLook`/`agentLook` in `apps/desktop/src/blob/look/index.ts` read back. **To avoid:** before writing a look from the daemon, check it against `valid_look`, not against the UI's `BlobLook` type.

## 2026-11-08 · Native shell · Thin lines crossed the window: a frame drawn before the window-state restore

**Symptom:** on first open, thin light lines ran down through the chat and across near the bottom, framing a rectangle smaller than the window, and then stayed.

**Root cause:** the main window is `transparent: true` and was created `visible: true` at the configured 1360×860 (`apps/desktop/src-tauri/tauri.conf.json`). `tauri-plugin-window-state` restores the saved geometry on the window-created event, which happens *after* the first frame is drawn (`tauri-plugin-window-state-2.5.0/src/lib.rs` 198–238: position, then size, then maximised, then `show`). A transparent WebView2 keeps the edges of the frame it painted at the configured size, so the frame and the window disagreed.

**Fix:** the window starts `visible: false`; the plugin is built with `StateFlags::all().difference(StateFlags::VISIBLE)`, so size, position and maximised still restore but visibility never does; the front end calls the new `main_window_ready` command from a 30 ms timer after its first render (`apps/desktop/src/main.tsx`; a timer, not animation frames, because a hidden WebView2 may not run them), which shows and focuses the window once (`static MAIN_WINDOW_READY`, label `main` only); and a setup thread shows the window anyway after 2.5 s if the call never comes, so a stuck page or an older bundle cannot leave the app invisible. Tray, single-instance and `show_main_window` are untouched.

**To avoid:** never create a transparent window at one size and resize it after its first paint — restore the geometry while the window is hidden, and make the first frame the one the person sees. When adding a command only the main window may call, copy `set_approval_badge`: take a `WebviewWindow` argument and reject anything whose `window.label()` is not `"main"`. **Application commands are not in the Tauri v2 ACL** — the generated `apps/desktop/src-tauri/gen/schemas/desktop-schema.json` has no row for `daemon_rpc` or `set_approval_badge` — so a capability entry for one is neither possible nor needed, and the label check is the whole restriction.

## 2026-11-01 · Storage · A correlated subquery made every conversation cost 250 to 400 ms

`session_detail_parts` read each turn's `turn.error` detail with a correlated subquery inside the turns statement. `EXPLAIN QUERY PLAN` shows `SCAN e` for that form, while the same lookup with the turn id bound as `?1` is `SEARCH … USING INDEX idx_app_events_turn_error`. SQLite would not seek the partial index for the correlated term, so it scanned the whole event log **once per turn**: 11.5 to 14.3 s for the log's 167 turns, about 74 ms a turn. A conversation with one turn cost about 75 ms and a busy one 1.2 s, although every statement measured on its own stayed under 10 ms — which is why the cost looked unexplainable and was blamed on the 380 MB of tool payloads instead.

Measured on a copy of the owner's 654 MB database (67 conversations, 4,972 tool calls, 150,966 events, 167 turns), `cargo run --release -p retinue-storage --example snapshot-timing -- <copy> --runs 5`:

| measure | before | after |
|---|---|---|
| `session.get`, median | 81 ms | **0.5 ms** |
| slowest conversation | 1,211 ms | **100 ms** (96 ms of it the tool payloads) |
| per-turn `turn.error` lookup, all 167 turns | 11,587 ms (`SCAN e`) | **1.7 ms** (`SEARCH … USING INDEX`) |
| full snapshot | 12.4 s | **1.0 s** |

Fix: read the turns without `detail`, then run one indexed lookup per turn with the id bound, and merge the value in (valid JSON stays a value, anything else stays a string, exactly as `json_object` embedded it). `turnDetailProof` in the tool proves `answersIdentical: true` for all 167 turns on the owner's data.

**To avoid:** never put a correlated subquery over `app_events` inside a per-row statement. Print the plan of the **whole** statement — a probe that times the inner `SELECT` alone shows the index being used and hides the scan. `--plans` in `snapshot-timing` prints the shapes side by side.

## 2026-11-01 · Architecture · Still slow after beta.48: what it loads and what it waits on

Second half of the day: measured on a copy of the owner's database (654 MB, 67 conversations, 4,972 tool calls, 167 turns) with `crates/retinue-storage/examples/snapshot-timing.rs`. The installed beta.48 felt like a heavy backend because of what the window loaded and what an action waited on, not because of Rust, Tauri or SQLite.

| measure | before | after |
|---|---|---|
| lazy snapshot (`app.snapshot?lazy`) | 8.1–8.8 s (keep 15); 4.96 s on this copy | **99 ms**, 2.1 MB (keep 0) |
| full snapshot | 21.8–22.5 s (12.4 s on this copy) | **1.0 s**, 13 MB |
| `session.get`, median | 81 ms | **0.5 ms** |
| effort save (`agent.update` + `session.model.update`, storage work) | 226 ms | **3.5 ms** |
| the same while every conversation is read back to back | 630 ms | **3.7 ms** |
| `task.create` + `task.dispatch` | 3.2 ms | 3.4 ms (the queue was never the cost; the writer lock was) |
| a write during a full background load | queued behind a snapshot (Settings waited up to 33.8 s in the first wave) | **0 ms median, 0.1 ms max** |

What changed:

- **Three read connections, not one.** `snapshot_reader`, `read_conn` (settings, `agent_get`, `session_event_summary`, `session_execution_row`) and `detail_conn` (a whole conversation). `session_detail`, `session_event_summary` and `agent_get` no longer take the writer lock. Every read runs in its own transaction, so read-after-write stays correct; `impl Drop` still closes readers first so the writer checkpoints the log.
- **A conversation loads when it is opened.** `App.tsx` fetched every partial conversation four at a time; now `conversationsToLoad` loads the open one plus the selected bot's newest two, one at a time, and nothing in the companion. A `session.changed` loads a transcript only for a conversation on screen — the row arrives in the event and `applyEvent` already merges it.
- **Startup sends summaries only.** `LAZY_SNAPSHOT_KEEP` is 0, so every at-rest conversation is a row plus its last three messages and no `tool_calls` row is read. A conversation with a turn running is still sent in full, because the window has nothing else to show.
- **An action reads the row, not the transcript.** `Storage::session_execution_row` is the conversation's own row plus its context counters; `session.model.update`, `session.model.plan` and `session.permissions.set` use it.
- **Effort is instant and honest.** The pill shows the chosen level while the save runs (`requestEffort` keeps the draft until it resolves; `triggerLabel` follows the draft), the bot and conversation writes run together (`Promise.allSettled`), and `agent.update` reads the model catalog **once**, from the cache (`Mode::CachedOnly`), instead of `Fresh` twice under two different Claude cache keys (one without the model hint, one with). A model change still writes the conversation first, so a cancelled one leaves both rows untouched. When no catalog is cached the values are accepted, which is what a failed probe already did.
- **A dropped task reads "Starting" at once**, before `task.dispatch` answers (`pendingDispatch`, UI only, never sent by the daemon), and goes back with the reason if it is refused.
- Still open: the tool payloads. 185 tool rows are 96 of one conversation's 100 ms, and 901 ms of the 993 ms the whole database costs to detail; the read-only-ids comparison is 17.8 ms. Fixing that needs `tool_calls` columns for kind/title/state and a tool-output-on-demand RPC, not a faster query.

**To avoid:** when a screen feels slow, time the RPC end to end on a copy before optimising any statement, and check which lock the action waits on. A per-conversation read on the writer lock queues every save behind it, however fast the query is.

## 2026-11-01 · Tests · An `Instant` can't go further back than the machine's uptime

`backup_import_of_an_expired_preview_is_not_found` failed in CI on `9f8fdae` and passed locally: the import succeeded after `expire_all`. The helper did `Instant::now().checked_sub(TTL + 1 s).unwrap_or_else(Instant::now)`. On Windows an `Instant` counts from boot, so on a runner up for less than 10 minutes `checked_sub` returns `None` and the preview is simply "created now". Inferred from the code; the runner's uptime wasn't read. Fix: store when a preview expires, not when it was made, so a test sets `expires` to now. Avoid: never fake the past by subtracting from an `Instant`.

## 2026-11-01 · Performance · The app feels slow everywhere at once: one lock, one huge snapshot

Symptom: skeleton loaders and "unsnappy" throughout, not tied to any one screen. Root cause, measured on a copy of the owner's real database (`<data>/retinue.db`, then 510 MB):

- `Storage` held **one** `Mutex<Connection>`, so every read queued behind the longest one.
- `app.snapshot` was the longest: lazy (15 fully detailed conversations) **304 ms and 3.1 MB of JSON**, full **1,297 ms and 9.6 MB**.
- Inside that, the per-session `tool_calls` query was a **full scan**: 383 MB in 3,973 rows (≈96 KB each of provider payload), with no index on `session_id`. With one: 318 ms → 137 ms. Reading only the ids: **3.4 ms**.

**Second wave, same day (done).** Numbers from `cargo run --release -p retinue-storage --example snapshot-timing -- <copy> --runs 3 --concurrent 20 --index` on a copy of the owner's **548 MB** database (65 open conversations, 4,310 tool calls, 141,692 events, 160 turns). The 304 ms figure above is not reproducible: this machine and this data give seconds. Measurements here vary ±30% with the page cache, so compare medians of three:

| measure | before | after |
|---|---|---|
| lazy snapshot | 8,080–8,828 ms (median) | 5,335 ms |
| full snapshot | 21,771–22,493 ms | 17,451 ms |
| `session_context_locked`, all 65 conversations | 2,172–2,982 ms (`SCAN app_events`) | 2.2 ms (`SEARCH … USING INDEX`) |
| `turn.error` detail read, all 160 turns | 23,209 ms (`SCAN e`) | 2.8 ms (`SEARCH … USING INDEX`) |
| `settings.get` while a snapshot runs | max 19,382–33,813 ms | max 8.6 ms |
| creating both indexes (once, at startup) | — | 143 ms + 115 ms |

- **A partial expression index on `app_events` is the fix for a `json_extract` lookup.** The `WHERE` must repeat every condition the query has — `event_type IN (…)` **and** `json_valid(payload)`, because `json_extract` raises on malformed JSON — and the query must say the same, or the planner silently keeps the scan. `ensure_read_indexes` now creates `idx_app_events_session_context` and `idx_app_events_turn_error`; `session_detail_parts`' turns query gained `json_valid(e.payload)` to match (proved identical for every turn on the real data).
- **Two read connections, not one shared one.** `app.snapshot` gets its own, and the small Settings reads (`settings.get`, the approval policy, `runtime.profile.list`) get another: one reader for both would have put Settings behind the snapshot again. In-memory databases have no second connection, so they fall back to the old single-connection path. Every read runs in its own transaction, which is also what makes a read see a write committed a moment earlier.
- **A read-only connection cannot checkpoint the log.** With readers open at close, the last connection to go is a reader, so `-wal` and `-shm` stayed on disk beside the database (`v1_migration_…rolls_back_in_temp_paths` failed with a stale log applied to a restored file). `impl Drop for Storage` closes the readers first, so the writer is still last and folds the log in.
- **`PRAGMA journal_mode=WAL` now runs on every file open**, not only the fresh-database branch; the readers rely on it.
- **`agent.update` only reads the model catalog when the save touches `runtimeId`/`model`/`thinking`/`serviceTier`.** `catalog::get(Mode::Fresh)` can start a provider probe, and an icon save was paying for it (and could silently fill in an effort level). The lock check stays first, and `validate_agent_catalog` still runs for the fields it validates.
- **A full `refresh()` after every action is what made the window feel slow**: it re-reads the whole snapshot. The send path, pull-request and review-comment sends, project creation, project restore and a scheduled conversation delete now rely on the reply plus the live events; `replay.gap` still reloads (that is the recovery), with a 250 ms window that turns a burst into one reload. Undo of a conversation delete still reloads: the snapshot is what puts the row back in its place.
- **An icon shows before the save:** a project's icon and a bot's look/colour are applied to the snapshot at once, and put back with the daemon's reason if the save is refused.
- **Not fixed, and measured:** one streamed token costs a whole-message rewrite plus a `message.delta` row: **2.6–11.6 ms** each on this database (`synchronous=FULL`, an fsync per commit). Batching it needs a flush before every non-delta event of that session to keep replay order, and a crash would drop the buffered tail of a partial message, so it was left. What is left of a snapshot is the per-conversation detail: 250–400 ms each, while each of its queries is under 10 ms on its own — the time goes on the ~380 MB of tool payloads the snapshot returns in full. That is the next thing to chase, and it needs the snapshot to carry less, not a faster query.
- **A UI test can depend on `refresh()` without saying so.** `App.emptyConversation` saw its auto-title only through the reloaded snapshot; with the reload gone the fixture has to emit the `session.changed` the daemon really sends.

**To avoid:** copy the database to a temp dir and time the exact SQL before optimising; never open the live file. Also: SQLite refuses `rowid` inside `CREATE INDEX` ("no such column: rowid") — index the column alone. For a read path nobody has timed end to end, write the timing tool first (`crates/retinue-storage/examples/snapshot-timing.rs`), and never edit an `app_events` query without re-reading the plan it prints.

## 2026-11-01 · Composer · `#` names a project now, not a side conversation

Owner decision: a bot works in many projects, so what a request needs to say is *where*, and `#` is the natural token. `#` in the composer now opens `ProjectPicker` (`teamSelectors.projectMatches`: exact name, then prefix, then substring, then tag). A new conversation's `projectId` is read back from the sent words (`projectNamedInText`), never kept beside them: a separate ref let the words and the folder disagree (a deleted `#Board` still opened in Board; a reopened draft showed `#Board` and opened elsewhere). Side conversations are still referenceable from a message's own menu (`MessageMenu` → `conversationRefs`), and `splitReferences` still renders stored ones.

The daemon resolves the same three ways in one place, `team::project_named`: id, exact name, unique tag, ignoring a leading `#`. An ambiguous tag or name is an error **naming the candidates**, so the Manager asks with real options instead of guessing; `message_blob`/`start_conversation`/`assign_task`/`propose_bot` all go through it. The Manager's instruction (team.rs) now says to read `#Name` from the message and to `ask_user` with the projects when none is named, and every bot is told that `#Name` is a project to pass on `message_blob` (an existing conversation stays in its folder). The approval card's `projectForDraft` resolves tags the same way, or a bot proposal shows the raw tag. The per-turn `<retinue_manager>` workspace block lists each project's tags.

The daemon no longer reads `Agent.defaultProject` (a path) to decide where a bot works: `external.rs project_path_of` dropped its fallback. The bot editor's "Working folder" box still writes it and `rosterSelectors.recentProjects` still lists it as a recent project, but it decides nothing — remove the box, that read and the column together when someone has the test fixtures to spare.

## 2026-10-31 · Daemon · An open conversation was left working in an emptied task copy

- **Symptom:** a real OpenCode bot in a fan-out replied without changing a file, and the transcript said "Nothing was changed, but the separate copy could not be removed." The copy was not there any more.
- **What Windows really does** (live, OpenCode 2.2.2): `git worktree remove --force` deletes every file and git's own record, then fails on the folder (error 32), because each `opencode acp` process has its first conversation's folder as its working folder. The branch survives. The folder stays, empty, and `worktree.abandoned` can't list it because git no longer knows it.
- **The next message was the real damage:** it reached the same live process, the bot reported an empty folder, and it wrote its file there. That folder is not a repository, so `inspect` failed silently in `after_task_turn` and no merge was offered, so the work was stranded with no error. A Claude bot hit the same discard (Sona's copy, in the 30 October entry on Auto approval mode). Two emptied copies were still on the owner's disk on this date: `which-model-are-you` and `hi-sona-you-are-the-backend-2`.
- **Merge and Discard on a merge card did the same**, with the same false "could not be removed", and left the conversation in the emptied folder with its branch kept.
- **Fix, four parts:**
  - `after_task_turn` no longer discards. A conversation that is open can get another message, so a copy with no changes stays, and it goes on the abandoned list once the conversation is deleted or archived. **The cost:** unchanged copies now last until then, including a read-only delegation's.
  - `worktree::remove_copy` counts an empty, unregistered folder as gone, for merge and discard. A folder with anything in it is still a leftover. `tidy_emptied_folder` clears the empty folder 45 seconds later (the ACP adapter stops an idle process after 30).
  - Merge and Discard close the conversation's agent (`close_agent`). An agent stays in the folder it started in whatever the database says, so changing `projectPath` alone left the next message in the old folder.
  - `worktree::restore`, run by `before_task_turn` at the start of `run_turn`, brings back a copy already emptied or deleted, from its branch. It checks for the `.git` file first, so a normal turn spawns no git. A folder with files in it is left alone and the owner is told. The project's setup steps are not rerun, so copied files such as `.env.local` don't come back.
- **Not a neutral working folder for the process.** A probe shows that frees the folder (only the process's working folder holds it; a session alone doesn't), but it covers OpenCode only, and the copy would still be removed under an open conversation.
- **OpenCode 2 ties a session to its folder.** `session/load` from another folder fails with -32602 "session ... does not belong to cwd". That wasn't on the ACP adapter's resume-rejected list, so the first message after a merge would have failed outright. It now starts a fresh session with the recap. Only the live run could show this; a stub adapter resumes anywhere.
- **Testing:** hold the folder with a single process (`ping`, not `cmd /c ping`, or the child outlives the kill). Holding a tracked file with `share_mode(0)` makes `git add -A` fail at random when git re-reads it; hold an ignored file when a merge has to get past `git add`.

## 2026-10-27 · Tooling · A "binary-safe" edit of storage `lib.rs` corrupted every non-ASCII character

## 2026-10-31 · Machines · What Phase 4 taught

## 2026-11-08 · Native (GPUI) fix round 2 · The window quit without a word

- **A panic in a GPUI window looks like a silent quit.** `native.log` ended with "daemon child stopped" and no "exited": the panic unwound through `Root`'s drop (stopping the daemon), then crossed an `extern "C"` boundary and aborted, so `main` never reached its last log line and the message went to a stderr nobody watches. Install a panic hook as the **first** thing in `main` (`trace::install_panic_hook`): it writes `PANIC at <file>:<line>:<col>: <message>` and a `std::backtrace::Backtrace::force_capture()` (which ignores `RUST_BACKTRACE`, so a debug build always has frames).
- **The cause was a GPUI double lease:** "cannot update Root while it is already being updated". `Entity::lease` *removes* the entity from the map while it is leased, so `entity.update`/`entity.read` on the same entity from inside its own listener or update panics, and the panic aborts the process.
  - The reported sequence reached it through `Ctrl+K`: the action listener holds `Root`, `toggle_quick` set the quick-switcher field's text, and the field's change hook called `root.update(..)` inside that.
  - The same shape was waiting in the composer: a keystroke's change hook read `self.composer`, Enter's submit handler cleared it, and Up/the `/command` menu updated it — all while the field was leased.
  - **Fix:** text-field hooks take the field itself (`Fn(&mut TextInput, ..)`, `Fn(&str, usize, ..)` for changes) and edit *it*; anything that needs the window goes through `Root`, which is a different entity. Programmatic `set_text`/`clear` do not fire the change hook at all. A listener that holds `Root` and needs to edit the field uses `Context::update_entity(&field, |input, cx| ..)`.
- **An overlay drawn by taking it out of the window disappears on the next repaint.** `render_menu_layer` did `self.menu.take()`, so the menu existed for exactly one frame; this window repaints every frame (marquee, working shimmer), which is why "…" never showed a popover. Overlays are drawn from `self.menu.clone()`.
- **`w_full()`/`min_w(0)` inside a content-sized parent is a percentage of nothing.** The user bubble is as wide as its text (up to its cap), so the inline-text block inside it collapsed to one character and a long message became a single column of letters down the whole pane. A bubble draws the shaped text itself (`styled_inline`); a block is only for parents whose width is settled.
- **Moving a transparent window programmatically leaves a strip of the old frame at its old edge.** Every "vertical band" screenshot taken after a `SetWindowPos` move had one; the same window started in place has none. Move it before it paints, or don't move it, when capturing.
- **A row answers the *press*, and over its whole area.** Two ways a card or a row can look alive and do nothing: the click sat on the inner block that holds the title, so a press on the card's own padding (which is drawn as the card and lights up on hover) was outside it; and `on_click` only fires when the same element is under the pointer at press *and* release, which a list that re-sorts, a fold that animates or a marquee that starts can break between the two. Rows that select or open (conversation cards, tree rows, the tree's conversation cards, the roster) bind `on_mouse_down`, and a button inside such a row (`…`) binds its own press and `stop_propagation`s it.
- **Guard the classes, not just the case:** `ui::guards` scans the source for the three shapes (a hook touching its own field, a method handed the box reaching the entity, an overlay taken instead of cloned, a bubble given a block).

## 2026-11-08 · Native (GPUI) fix round · What the first screenshot pass caught

- **A file chip must never start a program.** `explorer.exe <path>` on a path a bot wrote runs whatever it wrote: a `.bat`, `.ps1`, `.lnk` or `.exe` is one click away from executing. ## 2026-11-08 · Native (GPUI) slice 4 · Tasks, schedules, the rail, diffs and a terminal

- **`files::spawn_guard` blocks `taskkill`, so a terminal tab cannot take its whole process tree down.** The installed app's pty kills with `taskkill /T /F`; here that is a program started outside the three allowed call sites, and the guard fails the build. `portable_pty::Child::kill` ends the shell, a command the shell started can outlive it, and a job object (kill-on-close) is the way to do better.
- **A `const` array gives no `&'static` reference.** `&TEMPLATES[i]` on a `const` is a temporary; a closure that keeps the reference needs `pub static`. The schedule editor's "start from an idea" did.
- **`gpui` does not re-export taffy's `Position`.** A custom element that must overlay its parent needs `Style { position: Absolute, inset }` and cannot name the enum, so the terminal's grid size comes from `window.bounds()` minus the fixed column widths instead of from a measured element.
- **`Rgba` has no `opacity`; `Hsla` does.** A tinted diff row is `Rgba::from(Hsla::from(color).opacity(0.14))`, and `.bg()` takes either through `Background`, but a `match` arm that returns one and then the other will not type-check.
- **A slice's state belongs in one struct per area, with the root's hooks one line each.** Five fields on `Root` (`tasks`, `schedules`, `changes`, `terminal`, `delegations`) and five one-line hooks in `root.rs` kept the Director's restyling of `sidebar.rs`, `conversations.rs` and `conversation.rs` untouched.
- **A test expectation about a terminal is worth checking against what a terminal really does.** Backspace moves the caret and does not erase; a 3-row screen shrunk to 2 rows keeps the first two, not the last; a 4-row header block is four rows.

## 2026-11-13 · Daemon · A proxied frame: axum route shapes and the headers that must go

The computer's screen (`computer.view`, `computer.rs`) is the first route on the daemon's listener outside `/v1/*`. Three facts cost a build each:

- **A trailing slash is a different path.** `/computer/view/{ticket}` does not answer `/computer/view/<ticket>/`, and `{*rest}` does not match an empty remainder. Register both the bare ticket and the ticket-with-slash to the same handler, then the catch-all below them.
- **Buffer and strip `Content-Length`.** The proxy reads the whole upstream body, so any copied `Content-Length` (or `Transfer-Encoding`) contradicts the body axum writes. Strip both, with `Set-Cookie`, `Content-Security-Policy*`, `X-Frame-Options`, and add `Content-Security-Policy: frame-ancestors <app origins>`.
- **A frame cannot send the capability**, so the route is proved by a ticket in the path: 64 hex characters, compared in constant time against every live ticket, 10 minutes after last use, cleared on unlink. `desktop/src-tauri/tauri.conf.json` must add `frame-src 'self' http://127.0.0.1:*` or the app's own CSP blocks the frame. A WebSocket to the same path is forwarded with `tokio-tungstenite` (workspace dependency, promoted from dev-dependencies with `rustls-tls-webpki-roots` for `wss://`).

## 2026-11-13 · Machines · Starting and steering work on a linked machine is a local pass-through
