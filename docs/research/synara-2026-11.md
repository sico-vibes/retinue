# Synara, read against Retinue

> **What this is:** a read-only study of Synara (a T3 Code fork), its author's list of features, and what each item means for Retinue: what we already have with `path:line` evidence, what we lack, and what is worth building. No code was changed, nothing was committed, nothing was installed or run.
> **Status:** research; claims about Synara are its own documentation and source, checked on 18 November 2026, not a product review of a running app.
> **Last updated:** 2026-11-18

---

## Summary

**What Synara is.** A desktop workspace for coding-agent CLIs, forked from T3 Code at the end of March 2026, MIT-licensed, and developed separately since. It is public at [github.com/Emanuele-web04/synara](https://github.com/Emanuele-web04/synara) (2.3k stars, 5,567 commits) and [trysynara.com](https://www.trysynara.com). Its documentation is unusually candid: most pages carry a "source evidence" line naming the commit and files, and state what is *not* guaranteed. That is the one habit most worth copying.

**The short answer on the list.** The author's list has 17 shipped items and three "in progress". Of the 17, Retinue **has 2** (Hubs, in our shape: the CEO, delegations and sub-bots; saved browser logins, in our safer shape) and **partly has 3** (a per-project board without its Kanban view; computer control on other platforms; connector sign-in, where OAuth is built but unmerged). It **lacks 12**. Two of those gaps are not gaps for this owner: Synara's Computer Use is **macOS-only**, and Retinue already drives a Linux VPS and, behind a switch, the owner's own Windows PC; and its remote connections are a paid tier, while Retinue already spans a laptop, a home PC, a VPS and a phone. The three "in progress" items have one counterpart that matters — more MCP servers, which is exactly our connector catalogue — and two ("Synara Bots", a native design surface) we should not copy.

**The three worth doing first** (detail in section 4):

1. **Resume task** — a button that continues an interrupted or stopped turn without a new message. Synara shipped it in 1.6.1 and its model (`packages/shared/src/turnResume.ts`) is two cases: *resend* (never started) and *continue* (reached the provider, then died). Retinue already has the whole mechanism — `retry.rs` queues a `retry` item that "never resends the original prompt; it sends a literal continuation into the same session" (`crates/retinue-daemon/src/retry.rs:360-379`) — but only automatic retry uses it. Exposing it after a Stop or a crash is a small change and the one the owner asked for today.
2. **The board the owner can actually see.** `ui/TasksView.tsx:80` still draws "Kanban board — Coming soon", and every `task.*` method is `never` remote (`apps/desktop/src/remote/tiers.json:1594-1612`), so the board does not exist on the phone either. For someone running bots from four machines, the missing half is not a prettier column layout: it is task state on the devices he actually holds.
3. **Pin a message, keep a note.** Pinning is one table and one panel in Synara (migration `040_ProjectionThreadsPinnedMessagesNotes`), and Retinue has no in-chat pin at all. Cheap, quiet, and it fits the design language without a new surface.

**What to leave alone.** A Code OSS editor with TypeScript intelligence and a JavaScript debugger are a second IDE inside a Tauri window — a large build that duplicates what the owner already has, against this project's own "open in external editor" taste (`apps/desktop/src/tauri.ts:152`). Imported browser cookies would break the 14 November 2026 amendment (Retinue's own profile, no imported cookies). A public profile with agent stats contradicts the project's privacy line rather than merely costing effort.

**No conflict with AGENTS.md** is raised by items 1, 2, 3, split views, pinned messages, timed snooze, multi-folder projects (with care, section 4), or a Debug mode built as a skill. Two items do conflict: imported browser logins, and anything public-facing.

### The first three, in a little more detail

**1. Resume task.** Synara's model is worth copying exactly, because it names the two cases honestly. `turnResume.ts` returns `{kind:"resend", messageId}` when the newest request never started a turn, and `{kind:"continue", turnId, state}` when the latest turn reached the provider and ended `interrupted` or `error`; the comment says a continue's "old provider process is gone, so commands it ran must rerun". The guard list is explicit: nothing in flight, no pending approval or question, no queued follow-up, no delivery quarantine.

Retinue already has the harder half. `retry.rs:360-379` says: "The retry never resends the original prompt; it sends a literal continuation into the same session" — it queues a `retry` item with `meta.kind: auto_retry`, `retryOf`, `attempt`, and the text "Please continue.". It is triggered by provider errors and usage limits (bounded: `OVERLOADED_MAX_ATTEMPTS` 3, `RATE_LIMITED_MAX_ATTEMPTS` 2), and `queue.rs:578-591` pauses the queue after a failed or cancelled turn. What is missing is the owner's own trigger: after a Stop or a restart-lost turn, nothing offers to continue, so he types a sentence to get the same effect. The change is one RPC (`session.turn.resume {sessionId}`), the same guards, and one quiet line in `ComposerStatus` (`ui/PromptQueue.tsx`, already shows the paused queue with a Resume at `App.tsx:3222`). The honest sentence belongs on the card: "Commands it ran may need to run again."

**2. Task state on the phone.** `tiers.json:1601-1612` is explicit: "Task content is not projected to remote devices in this slice." That is a policy decision, not an accident, and it is the one that hurts most given the owner's phone-first day. The work is a redaction-and-projection job of the kind already done for `subbot.list` (`remote/policy.rs` drops `doingNow` and `error`), followed by a row in each of the two tables that read the policy. It should be planned with the threat model, not slipped in.

**3. Kanban.** `ui/TasksView.tsx:80` currently renders a placeholder for `view === 'kanban'`; the live board is `ui/DelegateBoard.tsx` (unassigned tasks, one lane per bot, drag to assign). Synara's columns are the useful part, because they are named for what the owner must do: Draft, In Progress, Awaiting you, Done, with Classic as the old three-column layout. Retinue's equivalent of "Awaiting you" already exists as `presentedSessionState` and the NeedsYou bell; the Kanban should read that, not invent a second status model.

## 6. The owner's question: pause a running task, resume it later

**Question as the owner put it:** "pause a running task cleanly, and resume it later from a resume task locked to that conversation and employee."

### What Synara does

| Control | What it does | Evidence |
|---|---|---|
| Composer **Stop** | "holds waiting follow-ups after the active turn settles"; a failed turn or a usage-limit rejection also pauses the queue; the notice offers **Resume**; the hold survives reload | [composer](https://www.trysynara.com/docs/features/composer#pause-and-resume-queued-messages), `queuedComposerPause.ts`, `queuedComposerDrain.ts` |
| **Resume task** (1.6.1) | Continues an interrupted or failed task "without adding a new chat message, or resends the existing message if its turn never started"; Enter on an empty draft | [composer](https://www.trysynara.com/docs/features/composer#resume-interrupted-work), `packages/shared/src/turnResume.ts` |
| **Thread goal** pause/resume | Pauses *continuation* and freezes the elapsed timer; a goal never takes priority over the owner's queued message | [thread goals](https://www.trysynara.com/docs/features/thread-goals) |
| **Pause hub** | Interrupts running work and stops new starts and automations | [hubs](https://www.trysynara.com/docs/features/hubs#pause-archive-and-delete) |
| Snooze | Postpones attention only: "it does not cancel a running turn" | [organize](https://www.trysynara.com/docs/features/organize#snooze-a-conversation) |

There is **no true mid-turn pause** anywhere in either app: a paused or interrupted turn loses its provider process. Synara says so plainly ("its old provider process is gone, so commands it ran must rerun"); T3's equivalent is a continuation message after the limit resets. "Pause" in all three products means *stop the turn, keep the conversation, offer a way back*.

### What T3 Code has

Our own study of T3 (`docs/research/competitor-adaptation-2026-11.md`, 10 Nov 2026) records: a durable server-side queue with `queue.resume` and `queued-run.start`; a thread-level `snoozedUntil`; and limit recovery that dispatches "Continue where you left off." with a deterministic message id after the reset, cancellable and snoozable (`:139-157`). T3's thread sidebar also settles and snoozes threads with an undo toast (`:226`). The owner's list says T3 has goals; I did not verify a goal control in T3 today.

### What Retinue has

| Capability | State | Evidence |
|---|---|---|
| Queue pause and resume | Paused on failed or cancelled turn when work is queued; paused on a failed send; paused after restart; `session.queue.resume` | `queue.rs:47-58,578-591,434-443` |

| Task pause | A global task pause and a concurrency cap | `tasks.rs:236,242` |
| Timed snooze | No; boolean only | `main.rs:1754`, `attention.rs:20-22` |

### What to learn, and what to build

1. **Their two-case honesty is better than our one case.** Ours always sends "Please continue." — good for a rate limit, wrong after a Stop (the owner stopped *because* he wanted to change something). A resumed turn should say which case it is, and refuse when the owner's last action was a Stop that came with edited instructions.
2. **No new message.** Their `continue` adds nothing to the transcript; ours would add a user row reading "Please continue.", which is why the retry item is marked `auto_retry` in `meta`. A user-triggered resume should be marked the same way so the transcript stays honest.
3. **The guard list is the whole design.** Nothing running, no pending approval or question, no queued item, and the turn must actually be `error` or `cancelled`. Retinue's `queue.rs` already refuses an active session; the missing guards are the approval and the queued item.
4. **"Locked to that conversation and employee"** is already how Retinue works: a conversation has one employee, and resuming is `session.resume` on that conversation. No new lock is needed — but the resume control must be shown only in that conversation, never as a global "resume everything", which is the one thing that could quietly replay stale work across four machines.

Concrete sketch: `session.turn.resume {sessionId}`, `never` remote, refusing unless the session is idle, the newest turn is `error` or `cancelled`, no permission request is pending and `queue_list` is empty; it queues a `retry` item with `meta.kind: "owner_resume"`, `retryOf: <turnId>`. One line in `ComposerStatus` when the same conditions hold, and the honest sentence on the card. That is an S, and it closes the owner's request without new reach.

## 7. Licence and attribution, if we ever adapt code

- Synara is **MIT** (`LICENSE`, two copyright lines: T3 Tools Inc. and Emanuele Di Pietro). MIT allows use, change and redistribution, including in a closed product, provided the copyright notice and the permission notice are included in all copies or substantial portions of the software. No copyleft, no per-file notice requirement.
- Because Synara itself is a fork of T3 Code (also MIT), a port of *their* code would carry **both** notices. Their repository keeps the T3 notice in `LICENSE`, which is exactly the duty we would inherit.
- Ideas are not copyrightable; expression is. Copying a shape of behaviour (two resume cases, a guard list, attention column names) needs no licence. Copying `turnResume.ts` verbatim does.
- House practice already exists: `docs/legal/third-party-notices.md` records ports of MIT interaction mechanics with the source commit, and says plainly that no component files or assets were included. A Synara-derived port would get one entry there with the commit `c8c1ed4` (or whichever we read), the file paths, and the two copyright lines.
- Nothing of their art, icons, name or wordmark should be taken: "Synara", the logo and the profile theme are their branding, and the design-language rules would refuse them anyway.
