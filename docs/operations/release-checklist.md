# Release checklist

> **What this is:** The checklist for each Retinue release: gates, publishing, digests, clean-up and open release items.
> **Status:** current
> **Last updated:** 2026-11-17

**Two refusals added on 17 November 2026 (wave 3, `docs/plans/nod-adoption-plan.md`, release safety).**
The **Release build** workflow now starts with a `require-ci` job: it refuses to build unless
`.github/workflows/ci.yml` has a successful run whose newest run on that exact commit concluded
success, so there is no way to build a release from a red commit (re-run CI first; a dispatch on a
commit CI never ran is refused too). And `scripts/release-windows.ps1` reads the `latest.json` it
just wrote back through `scripts/update-round-trip.mjs`, the same field rules the installed build's
updater applies, and refuses a version that is not newer than the one `channel-beta` currently
offers (it asks `gh` for the published manifest; a dry run checks the shape only). What only CI can
prove: that the `require-ci` job's `gh api` query matches this repository's workflow ids, and that a
green nightly run keeps the split jobs honest.

Updated 14 November 2026. `v0.2.0-beta.4` is published and is the newest versioned GitHub release. Beta.32 introduced the new updater key; It is signed for the updater with a **new key** (the beta.6 key was not on this machine; owner decision 18 October), and the rolling `channel-beta` manifest now offers 0.2.0-beta.4. Installs older than beta.32 carry the old public key and must install beta.32 by hand; from beta.32 on, the app downloads updates itself. No clean-machine install has been recorded. Status values are `done`, `needs user`, or `blocked`.

Versions read from this worktree: root `package.json`, `package-lock.json`, `apps/desktop/package.json`, `apps/desktop/src-tauri/tauri.conf.json`, and the workspace `Cargo.toml` `[workspace.package].version` are all `0.2.0-beta.4`. Cargo.lock entries for the 15 crates inheriting the workspace version are 0.2.0-beta.4; the internal `retinue-agent-core` and `retinue-protocol` libraries remain independently versioned at `0.1.0`. The desktop crate `retinue-desktop` uses `version.workspace = true`. Product name is `Retinue`, `mainBinaryName` is `Retinue` (so the executable is `Retinue.exe`), and the identifier is `com.retinue.desktop` (development builds use `com.retinue.desktop.dev`).

`docs/releases/0.2.0-beta.4.md` is the published note for the current beta. The signed release script is not used for unsigned manual releases. For a future signed release, `scripts/release-windows.ps1` refuses to publish until the four version fields above equal the `-Version` argument.

`-DryRun` runs preflight, the bundle build, and manifest generation, prints the `gh` commands it would run, and does not execute `gh`, create a tag, or push. Add `-SkipBuild` to reuse an existing NSIS output directory, and `-BundleDir` to point that directory at a folder of `*-setup.exe` and matching `.sig` files (used to exercise the script without a real bundle). `-Repo` defaults to `sico-vibes/retinue`.

`npm run desktop:bundle` runs `scripts/bundle-windows.ps1`, which:

1. Sets `CARGO_TARGET_DIR` to `target\desktop-release` when the variable is unset.
2. Runs `cargo build -p retinue-daemon --bin retinued -p retinue-hook --bin retinue-hook --release`.
3. Runs `node scripts/stage-daemon.mjs --release`, which copies the sidecars to `apps/desktop/src-tauri/binaries/` with the Tauri target-triple suffix.
4. Runs `npm run desktop -- build`, which is `tauri build` for `@retinue/desktop`.

The bundled installer is `Retinue_<version>_x64-setup.exe`: its name follows `bundle > productName` (`Retinue`), and the packaged executable is `Retinue.exe` (the `mainBinaryName`). A generated NSIS script derives the per-user install directory `%LOCALAPPDATA%\Retinue` and the uninstall key `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\Retinue` from `productName`.

The installer has no custom NSIS hooks. The pre-install hook from FIX11 (`installer-hooks.nsh`) was removed on 2026-11-10: after the rebrand it matched the current uninstall key, so every manual reinstall force-closed Retinue and silently uninstalled it first, and that `taskkill /F` plus silent uninstall is behaviour antivirus heuristics treat as suspicious.

The release artifact is the NSIS installer only. An MSI is not a Retinue release artifact: an MSI version cannot carry a `-beta.N` pre-release. `docs/operations/updater.md` sets the Windows bundle target to `nsis` only. The release script globs `<CARGO_TARGET_DIR>\release\bundle\nsis\*-setup.exe`, keeps the file whose name matches the release version, and requires the sibling `<installer>.sig`. It does not upload an MSI.

`apps/desktop/src-tauri/tauri.conf.json` has `bundle.targets: ["nsis"]`, `createUpdaterArtifacts: true`, the updater public key, and the stable endpoint in `plugins.updater.endpoints`. The beta endpoint is not in that file: `apps/desktop/src-tauri/src/updates.rs` (lines 19-21 and 231-234) sets the endpoint per channel. For beta.8 only, the build overrode `bundle.createUpdaterArtifacts` to `false` and passed `--no-sign`; this produced no `.sig` and no `latest.json`. The rolling beta channel was left unchanged.

The beta.6 bundle run staged both `retinued-x86_64-pc-windows-msvc.exe` and `retinue-hook-x86_64-pc-windows-msvc.exe` in `apps/desktop/src-tauri/binaries/` for packaging. These are local bundle outputs, not source changes. (Before FIX11 these sidecars were named `retinued-*` and `retinue-hook-*`.)

## Update manifest and channels

Status: **done for beta.6**. The signed `latest.json` is attached to `v0.1.0-beta.6` and the rolling `channel-beta` asset remains at version `0.1.0-beta.6`; unsigned manual-only beta.7 and beta.8 do not replace it.

`scripts/make-update-manifest.mjs` writes the Tauri updater static file `latest.json`:

`{ "version", "notes", "pub_date", "platforms": { "windows-x86_64": { "signature", "url" } } }`

Notes come from `docs/releases/<version>.md`. If that file is missing or blank, the note is the single line `Retinue <version>`. The signature is the trimmed `.sig` file. The asset URL is `https://github.com/<repo>/releases/download/v<version>/<installer file name>`.

| Channel | Gets | Manifest URL |
| --- | --- | --- |
| `stable` | non-pre-release releases only | `https://github.com/sico-vibes/retinue/releases/latest/download/latest.json` |
| `beta` (default while only betas exist) | every release, beta or stable | `https://github.com/sico-vibes/retinue/releases/download/channel-beta/latest.json` |

`releases/latest` ignores pre-releases, so the stable URL only resolves once a normal release exists. `channel-beta` is a rolling pre-release. Its only job is to hold the newest `latest.json`. On every release the script creates `channel-beta` if it does not exist (`--prerelease`, `--latest=false`, `--target main`, fixed short note) and then runs `gh release upload channel-beta latest.json --clobber`. The same `latest.json` is also attached to the versioned release. Installer URLs inside the manifest point at that versioned release's NSIS asset.

The release script reads the private key and password only while `npm run desktop:bundle` runs, from `%USERPROFILE%\.retinue-release\updater.key` and `updater.pass`, or from `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` when those are already set. It then removes them from the process environment. It does not print them.

The public half is configured in `apps/desktop/src-tauri/tauri.conf.json` under `plugins.updater.pubkey` (`docs/operations/updater.md`).

Losing the private key means existing installs cannot accept future updates: the app keeps the old public key and will reject signatures from a new key. Never commit `updater.key`, `updater.pass`, or the private-key environment values. The release script loaded the existing files into its build process and removed them from the process environment afterward.

6. Stable installs then resolve `https://github.com/sico-vibes/retinue/releases/latest/download/latest.json`. Beta installs keep using the `channel-beta` URL above.

Use `-DryRun` first. A dry run still needs the updater signing key if it is allowed to build.

## Content security policy

Status: **done** (present in `app.security.csp`; not exercised in a WebView)

The policy is one line in `apps/desktop/src-tauri/tauri.conf.json`. Remote and special origins it allows:

| Directive | Origins |
| --- | --- |
| `default-src`, `script-src`, `base-uri` | `'self'` only. Scripts are not loaded from a network host. |
| `style-src` | `'self'` and `'unsafe-inline'` (inline style attributes in the shell). |
| `img-src` | `'self'`, `asset:`, `http://asset.localhost`, `blob:`, `data:` |
| `font-src` | `'self'`, `data:` |
| `connect-src` | `'self'`, `ipc:`, `http://ipc.localhost`, `http://127.0.0.1:1420`, `ws://127.0.0.1:1420` |
| `object-src` | `'none'` |
| `frame-ancestors` | `'none'` |

`http://asset.localhost` and `http://ipc.localhost` are the Tauri asset and IPC hosts. `127.0.0.1:1420` is the local Vite dev server (HTTP and WebSocket). No public internet origin is listed. The dev port is also what `beforeDevCommand` / `devUrl` use. A generated dev config can retarget that port; the committed policy names 1420.
